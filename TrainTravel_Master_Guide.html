GW

Microservices Architecture & API Gateway

Express · Reverse Proxy · Circuit Breaker · Rate Limiting
System Perimeter
💡 Plain English Explanation

Imagine a huge shopping mall with specialized shops: a bakery, a shoe store, a jewelry shop, and a security office. Instead of letting shoppers wander into employee backrooms, there is a grand front entrance with a helpful concierge.

The API Gateway is the concierge: it checks your ID card (JWT token), makes sure you aren't running in and out 100 times a second (rate limiter), and directs you straight to the exact shop you need.

⚙️ In-Depth Technical Specification

Microservices decompose monolithic state into autonomous domain bounded contexts (DDD):

  • Single Entrypoint: The Gateway exposes port 4000, decoupling clients from internal service ports and topology.
  • Cross-Cutting Concerns: Handles central JWT decoding, IP-based sliding window rate limiting, CORS, Helmet security headers, and request logging.
  • Circuit Breaking: Monitors downstream HTTP latency and error rates, failing fast if a service goes down to prevent cascading thread starvation.
🎯 Exact Role in TrainTravel

Located in api-gateway/src. It routes /api/users/* to Port 4001, /api/search/* to 4002, /api/admins/* to 4003, /api/bookings/* to 4005, /api/payments/* to 4006, and /api/inventory/* to 4007.

Crucially, it intercepts Razorpay webhooks to parse raw byte streams for HMAC cryptographic signature verification before routing.

SQL

PostgreSQL 15, Prisma ORM & Row Locking

ACID · FOR UPDATE NOWAIT · Segment Locks · Advisory Locks
Zero Double-Bookings
💡 Plain English Explanation

Imagine a train seat has a physical wooden token on the ticket counter. When two travelers rush to grab Seat 14A at the exact same millisecond during a festival rush, only one person's hand touches the token first.

Database Row-Level Locking guarantees that the second person is told immediately: "Sorry, someone else just locked this seat!" without causing a fight or double-selling the ticket.

⚙️ In-Depth Technical Specification

PostgreSQL provides strict serializability and row-level exclusivity:

  • FOR UPDATE NOWAIT: Immediately acquires an exclusive row lock on seat_inventories. If another transaction holds the lock, PostgreSQL rejects the call with error code 55P03 instantly rather than blocking worker threads.
  • Retry with Backoff: Wrapped in retryTransaction with exponential jitter to resolve transient lock contention.
  • Segment Overlap Math: seat_segment_locks queries check (fromSeq < requestToSeq) AND (toSeq > requestFromSeq) to verify segment seat availability.
🎯 Exact Role in TrainTravel

Implemented in inventory-service/src/services/inventory.service.js.

It allows seats to be booked by passenger A from Delhi to Jaipur (Stops 1→2) and reused by passenger B from Jaipur to Mumbai (Stops 2→5) on the exact same train schedule! Background leader election utilizes pg_try_advisory_lock(800001) so only one instance cleans up expired seats.

SAGA

Saga Pattern (Orchestration & Compensation)

Distributed Transactions · Eventual Consistency · Audit Log
Distributed Consistency
💡 Plain English Explanation

Imagine planning a trip: 1) You hold the train seat, 2) You swipe your credit card, 3) You get your ticket.

What if your credit card payment fails after the seat was held? A Saga Orchestrator is the conductor who steps in, cancels the hold, releases the seat back to the general public, and updates your account cleanly without leaving orphaned records.

⚙️ In-Depth Technical Specification

In a distributed Database-per-Service architecture, classic ACID transactions (2PC) do not scale and introduce locking bottlenecks. The Saga Pattern replaces them:

  • Forward Sequence: HOLD_SEATS $\rightarrow$ CREATE_PAYMENT $\rightarrow$ CONFIRM_SEATS $\rightarrow$ COMPLETE.
  • SagaLog Persistence: Every step records state (PENDING, COMPLETED, FAILED) with input/output payloads in the database for crash recovery.
  • Compensating Actions: On failure or timeout, the orchestrator triggers rollback steps in exact reverse order: compensateConfirmSeats $\rightarrow$ compensateCreatePayment (refund) $\rightarrow$ compensateHoldSeats (release lock).
🎯 Exact Role in TrainTravel

Built inside booking-service/src/services/saga.service.js.

Coordinates HTTP RPC calls between Booking, Inventory, and Payment services. If payment fails or times out, compensateAll() guarantees that locked seats are immediately released and refund records are generated idempotently using unique key hashes.

KAFKA

Apache Kafka (Event-Driven Asynchronous Streaming)

KafkaJS · Dead Letter Queues · Pub/Sub · Event Sourcing
Asynchronous Nervous System
💡 Plain English Explanation

When a train arrives at a station, the central station announcer doesn't walk up to every passenger and whisper in their ear. They broadcast over the public speaker system once.

The display board updates, the cafeteria prepares food, and the taxi drivers line up outside. Kafka is that reliable public speaker system. It broadcasts events across all services without waiting for anyone to finish listening.

⚙️ In-Depth Technical Specification

Kafka is a distributed partitioned commit log providing high throughput and fault tolerance:

  • Decoupling & Non-Blocking I/O: Critical transactional paths don't wait on slow third-party operations (like sending emails or syncing search indexes).
  • Dead Letter Queue (DLQ): If a consumer fails to process a message after 3 retries (DLQ_MAX_RETRIES = 3), it is moved to a dedicated DLQ topic (e.g. dlq.booking-service) to prevent poison pill consumer crashes.
  • Idempotent Event Consumers: Every event carries an eventKey verified against an IdempotencyRecord table to prevent duplicate processing.
🎯 Exact Role in TrainTravel

Defined centrally in shared/constants/kafka-topics.js.

When an Admin creates a schedule, Kafka publishes admin.schedule-created. Inventory Service ingests it to generate seat matrix rows, while Search Service indexes it in Elasticsearch. Notification Service consumes notification.otp-email and booking.confirmed without slowing down user responses.

Sub-Millisecond Speed

If a teacher asks you what 12 × 12 is, you don't open a calculator and compute it manually; you recite "144" from immediate memory in half a second.

Redis is the lightning-fast short-term memory. It holds frequently requested user profiles and temporary 6-digit OTP codes in ultra-fast RAM so the main database isn't burdened.

⚙️ In-Depth Technical Specification

Provides multi-device logout, brute-force OTP protection (maximum 3 failed verification attempts before auto-delete), and fast profile lookups before touching PostgreSQL.

System Design Challenges & Computer Science Rationale

The hard engineering problems solved in TrainTravel to guarantee zero double bookings and eventual consistency

01

Preventing Seat Double-Bookings Under High Concurrency

Critical Concurrency
⚠️ Why Optimistic Locking Fails During Peak Booking

In high-velocity flash sales (like Indian Railway Tatkal opening), 10,000 users try to book the exact same 50 seats in the first 2 seconds.

If you use simple optimistic locking (e.g. WHERE version = 1), 9,990 transactions will fail at commit time, triggering massive cascading database rollbacks, wasted CPU cycles, and terrible user experience.

🛡️ TrainTravel's Dual Locking Architecture

TrainTravel enforces Pessimistic Row-Level Locking with NOWAIT:

  • SELECT ... FOR UPDATE NOWAIT: Locks the specific seat rows in PostgreSQL immediately. If another transaction holds the lock, it fails instantly instead of waiting in a blocking queue that exhausts database connection pools.
  • Retry with Jitter: Wrapped in retryTransaction with exponential backoff (100ms, 200ms, 400ms) to smoothly absorb transient lock contention.
  • Distributed Advisory Leader Election: Running seat lock cleanup every 15 seconds across multiple container instances is dangerous. We use SELECT pg_try_advisory_lock(800001) so exactly one instance executes the cleanup job without distributed race conditions!
02

Dynamic Route Topology & Segment Seat Reuse

Mathematical Interval Algebra
📐 The Problem with Monolithic Seat Allocation

A train runs from Delhi (Seq 1) $\rightarrow$ Jaipur (Seq 2) $\rightarrow$ Ahmedabad (Seq 3) $\rightarrow$ Mumbai (Seq 4).

In naive systems, booking Seat 12 from Delhi to Jaipur marks Seat 12 as "BOOKED" for the entire journey. That prevents someone from booking Seat 12 from Ahmedabad to Mumbai, leaving train coaches half-empty and losing thousands of dollars in ticket revenue!

🚀 TrainTravel's Interval Overlap Algorithm

TrainTravel introduced seat_segment_locks, which decouples physical seats from journey segments:

PostgreSQL Segment Overlap Check 
/* Two intervals [A_from, A_to] and [B_from, B_to] overlap IF AND ONLY IF:
   A_from < B_to AND A_to > B_from */
SELECT "seatId" FROM seat_segment_locks
WHERE "scheduleId" = ${scheduleId}
  AND "seatId" = ANY(${seatIds}::text[])
  AND status IN ('LOCKED', 'BOOKED')
  AND "fromSeq" < ${toSeq}
  AND "toSeq" > ${fromSeq}
FOR UPDATE NOWAIT;

If no overlap exists, passenger B can book Seat 12 from Ahmedabad to Mumbai even while passenger A is sitting in it from Delhi to Jaipur!

03

Saga Orchestration vs Two-Phase Commit (2PC)

CAP Theorem Trade-Off
⚠️ Why 2PC Fails in Cloud Microservices

Two-Phase Commit (2PC) requires a central coordinator to lock all participating database rows across multiple network servers simultaneously until everyone votes "YES".

If the Payment Gateway or external network hiccups, all seats across Postgres instances remain locked indefinitely, degrading system availability (violating the CAP theorem).

🛡️ Orchestrated Saga with Audit Log

TrainTravel embraces Eventual Consistency via the Saga Orchestrator:

  • Local Transactions: Each service commits its changes locally within its own database without holding distributed locks across the network.
  • SagaLog Table: Records every state transition (HOLD_SEATS, CREATE_PAYMENT, CONFIRM_SEATS) with JSON payloads in PostgreSQL.
  • Compensating Actions: If a user closes their browser or Razorpay reports a payment failure, the orchestrator triggers compensateAll(): issuing automated refunds and unholding seats asynchronously.
04

Dead Letter Queues (DLQ) & Poison Pill Resilience

Fault Tolerance
⚠️ What is a "Poison Pill" Message?

Imagine a Kafka message arrives with corrupted JSON (e.g. missing an email address). If the consumer crashes every time it reads it, Kafka will re-deliver the exact same message forever.

The consumer gets stuck in an infinite crash loop, halting all legitimate ticket confirmations for all other users!

🛡️ TrainTravel's DLQ Architecture

Centrally configured in shared/constants/kafka-topics.js:

  • DLQ_MAX_RETRIES = 3: If a message fails processing 3 times in a row, the consumer logs an alert and pushes the payload to a dedicated service DLQ (e.g. dlq.booking-service).
  • Unblocked Partitions: Kafka partition offsets advance smoothly so subsequent booking events are never blocked by a single malformed packet.
  • Idempotency Records: Every consumer checks IdempotencyRecord table to ensure network retransmits never create duplicate inventory or double charges.
05

Multi-Key Redis Distributed Locking via Atomic Lua Scripts & Deadlock Prevention

Distributed Concurrency
⚠️ Why Standard Redis SET NX / MULTI Fails for Multi-Seat Reservations

When a family books 4 seats together (e.g. Seats 12, 13, 14, 15), acquiring locks sequentially over HTTP/TCP introduces severe race conditions. If User A locks Seat 12 and User B locks Seat 13, both users get stuck holding half a reservation (partial allocation).

Furthermore, standard Redis MULTI / EXEC transactions cannot inspect state mid-flight: they queue commands blindly without the ability to roll back if an earlier key fails. If two users lock the same set in reverse order ([12, 13] vs [13, 12]), a classic distributed deadlock (Dining Philosophers problem) occurs.

🛡️ TrainTravel's Atomic Lua Engine & Key Sorting

Engineered in booking-service/src/utils/distributedLock.js:

  • Deadlock Prevention via Key Sorting: All seat IDs are sorted lexicographically ([...seatIds].sort()) before constructing keys. Every concurrent worker acquires locks in the exact same deterministic global order, mathematically eliminating circular wait conditions!
  • All-or-Nothing Atomic Lua Evaluation: We execute an atomic Lua script directly inside the Redis engine:
    for i, key in ipairs(KEYS) do ... if not result then for j = 1, #acquired do redis.call('DEL', acquired[j]) end return 0 end.
    If even a single seat is unavailable, Lua automatically unrolls and deletes all previously acquired locks in the batch, returning 0 without network round-trips!
  • Safe Release with Ownership Verification: The release Lua script verifies that redis.call('GET', key) == lockValue before deleting, guaranteeing that a delayed request never accidentally releases a lock owned by a subsequent booking.
06

Distributed Leader Election (Redis vs PostgreSQL) & Optimistic CAS Race Prevention

Horizontal Scalability
📐 Multi-Pod Background Jobs & Payment Race Hazards

When running 5 autoscaled replicas of booking-service and inventory-service, background cleanup cron jobs running every 30 seconds can unleash chaos: all 5 pods scan the database simultaneously, compete for row updates, and send 5 duplicate Kafka cancellation notifications.

Even worse is the Payment Webhook Race Hazard: User pays at second 599. At second 600, Razorpay's webhook arrives at payment-service while simultaneously the background expiry job wakes up in booking-service. If the expiry job cancels the booking without checking whether payment succeeded, the customer is charged but loses their ticket!

🛡️ Dual Leader Election & Versioned Optimistic Locking (CAS)

TrainTravel implements a multi-layered defense:

  • Redis Leader Election: In booking-service/src/utils/bookingExpiry.js, pods compete via redis.set('booking:expiry-job:leader', pid, 'NX', 'EX', 25). Exactly one pod wins the lease per 30-second cycle; non-leaders immediately yield.
  • PostgreSQL Advisory Lock Leader Election: In inventory-service/src/utils/lockExpiry.js, instances call SELECT pg_try_advisory_lock(800001). The engine allocates a dedicated 64-bit application-level lock without touching table rows.
  • Optimistic Compare-And-Swap (CAS) Versioning: When expiring a booking, we execute:
    prisma.booking.updateMany({ where: { id: booking.id, version: booking.version, status: { in: ['PENDING', 'SEATS_HELD', 'PAYMENT_PENDING'] } }, data: { status: 'EXPIRED', version: { increment: 1 } } }).
    If the concurrent payment webhook increments version first, claimed.count === 0! The expiry job safely backs off without cancelling a paid ticket!
07

Cryptographic Timing Attack Prevention & Client Device Fingerprinting

Application Security (AppSec)
⚠️ Side-Channel Timing Vulnerabilities & Token Hijacking

Standard string equality in JavaScript (storedOtp === inputOtp) returns false at the first mismatching character. Comparing "123456" against "987654" terminates in ~12 nanoseconds, while comparing against "123459" terminates in ~45 nanoseconds.

Over local networks or low-jitter fiber connections, sophisticated attackers measure statistical response latency variance to progressively deduce OTP digits without brute-forcing all $10^6$ combinations! Furthermore, stolen JWT tokens can be replayed from rogue browser sessions.

🛡️ TrainTravel's AppSec Implementation

Implemented in user-service/src/utils/otp.js & deviceFingerprint.js:

  • Constant-Time Verification: We compute HMAC-SHA256 over ${email}:${otp} and verify using crypto.timingSafeEqual(Buffer.from(hashedOtp, 'hex'), Buffer.from(storedOtp, 'hex')). Execution duration is mathematically identical regardless of mismatch position!
  • Hardware & Header Device Fingerprinting: Every request generates a deterministic 16-character SHA-256 fingerprint: crypto.createHash('sha256').update(`${userAgent}|${ip}|${accept}`).digest('hex').slice(0, 16). Sessions and refresh tokens are bound to this fingerprint.
  • Zero-Trust Internal Network Headers: Internal endpoints require x-internal-service-key verified by internalAuth.middleware.js, and x-user-id is strictly propagated from the verified API Gateway JWT claim.
08

Pluggable Payment Gateway Strategy Pattern & Raw Byte Webhook Verification

Design Patterns & PSP Architecture
⚠️ Why JSON Parsing Breaks Cryptographic Webhook Signatures

When payment gateways like Razorpay dispatch webhooks, they attach an HTTP header x-razorpay-signature generated by computing an HMAC-SHA256 signature across the raw binary byte stream of the incoming request body.

If an Express gateway uses default express.json(), it parses the payload into a JavaScript Object and re-serializes it when proxying downstream. Re-serialization changes object key order, spacing, and UTF-8 encoding, breaking the cryptographic signature and causing genuine payment confirmations to be rejected!

🛡️ TrainTravel's Factory Pattern & Raw Stream Pipeline

Engineered in payment-service & api-gateway/src/index.js:

  • Raw Buffer Interceptor: In api-gateway/src/index.js, the webhook route is conditionally intercepted:
    if (req.path === '/api/payments/webhooks/razorpay') { express.raw({ type: 'application/json' })(req, res, next); }.
    The uncorrupted raw buffer reaches the signature verifier with 100% cryptographic byte fidelity.
  • Polymorphic Gateway Strategy Pattern: In payment-service/src/services/gateways/, we define an abstract BaseGateway class with standard interfaces (createOrder, verifyPayment, refundPayment, verifyWebhookSignature).
  • Singleton Factory: gateway.factory.js dynamically instantiates RazorpayGateway (or Stripe/PayPal) based on the PAYMENT_GATEWAY environment variable, enabling hot-swappable payment service providers without altering a single line of booking business logic!

▼

What Problem It Solves

Eliminates seat double-booking under extreme concurrent requests while supporting segment-based seat reuse (booking Delhi-to-Jaipur and Jaipur-to-Mumbai on the same seat).

Key Architectural Patterns

PostgreSQL FOR UPDATE NOWAIT, segment overlap math, transaction retries with exponential backoff, and aggregate counter recalibration to prevent counter drift.

inventory-service/src/services/inventory.service.js (lockSeats implementation) 
const lockSeats = async (scheduleId, seatIds, userId, ttlSeconds, fromSeq, toSeq) => {
  const ttl = Math.min(Math.max(ttlSeconds || config.LOCK_TTL_SECONDS, 60), 600);
  const lockExpiresAt = new Date(Date.now() + ttl * 1000);

  return retryTransaction(async () => {
    return prisma.$transaction(async (tx) => {
      // 1. Acquire exclusive row lock immediately without blocking connection pool
      const seats = await tx.$queryRaw`
        SELECT id, "seatId", "seatNumber", status, "lockedBy"
        FROM seat_inventories
        WHERE "scheduleId" = ${scheduleId}
        AND "seatId" = ANY(${seatIds}::text[])
        FOR UPDATE NOWAIT
      `;

      // 2. SEGMENT BOOKING: Check for overlapping locks in the requested segment
      if (fromSeq && toSeq) {
        const overlapping = await tx.$queryRaw`
          SELECT "seatId" FROM seat_segment_locks
          WHERE "scheduleId" = ${scheduleId}
          AND "seatId" = ANY(${seatIds}::text[])
          AND status IN ('LOCKED', 'BOOKED')
          AND "fromSeq" < ${toSeq}
          AND "toSeq" > ${fromSeq}
          FOR UPDATE NOWAIT
        `;

        if (overlapping.length > 0) {
          throw new ConflictError('Seats already locked for overlapping segment');
        }

        // 3. Persist segment locks for each seat
        for (const seat of seats) {
          await tx.seatSegmentLock.create({
            data: { scheduleId, seatId: seat.seatId, fromSeq, toSeq, status: 'LOCKED', lockedBy: userId, lockExpiresAt }
          });
        }
      }
      // 4. Recalculate and update schedule availability aggregates
      return { scheduleId, lockExpiresAt, lockedSeats: seatIds };
    });
  });
};

// Step 1: Forward Seat Hold
async function executeHoldSeats(booking, seatIds, ttlSeconds, fromSeq, toSeq) {
  const sagaLog = await prisma.sagaLog.create({
    data: { bookingId: booking.id, step: 'HOLD_SEATS', status: 'PENDING' }
  });
  try {
    const result = await inventoryClient.holdSeats(booking.scheduleId, seatIds, booking.userId, ttlSeconds, fromSeq, toSeq);
    await prisma.sagaLog.update({ where: { id: sagaLog.id }, data: { status: 'COMPLETED', response: result } });
    return result;
  } catch (error) {
    await prisma.sagaLog.update({ where: { id: sagaLog.id }, data: { status: 'FAILED', error: error.message } });
    throw error;
  }
}

// Step 2: Reverse Compensating Rollback
async function compensateAll(booking, seatIds) {
  const completedSteps = await prisma.sagaLog.findMany({
    where: { bookingId: booking.id, status: 'COMPLETED' },
    orderBy: { createdAt: 'desc' } // Reverse order!
  });

  for (const step of completedSteps) {
    if (step.step === 'CONFIRM_SEATS') await compensateConfirmSeats(booking);
    if (step.step === 'CREATE_PAYMENT') await compensateCreatePayment(booking);
    if (step.step === 'HOLD_SEATS') await compensateHoldSeats(booking, seatIds);
  }
}

const ADVISORY_LOCK_ID = 800001;

async function tryAcquireLeadership() {
  const result = await prisma.$queryRaw`SELECT pg_try_advisory_lock(${ADVISORY_LOCK_ID}) AS acquired`;
  return result[0].acquired === true;
}

async function cleanExpiredLocks() {
  const isLeader = await tryAcquireLeadership();
  if (!isLeader) return; // Skip if another instance is already running cleanup

  try {
    // Find expired segment locks past TTL
    const expired = await prisma.seatSegmentLock.findMany({
      where: { status: 'LOCKED', lockExpiresAt: { lt: new Date() } }
    });
    // Delete locks & recompute seat statuses
    await prisma.$executeRaw`DELETE FROM seat_segment_locks WHERE id = ANY(${expired.map(l => l.id)}::text[])`;
  } finally {
    await prisma.$queryRaw`SELECT pg_advisory_unlock(${ADVISORY_LOCK_ID})`;
  }
}

booking-service/src/utils/distributedLock.js Atomic Lua Distributed Lock Core
▼

Deadlock Prevention Algorithm

Sorts seat keys lexicographically ([...seatIds].sort()) to guarantee all concurrent workers acquire locks in identical global order, eliminating circular wait conditions.

All-or-Nothing Atomic Rollback

Runs a custom Lua script inside Redis. If even one seat in the reservation is unavailable, Lua unrolls and deletes all previously acquired keys in that transaction, returning 0 without network round-trips.

booking-service/src/utils/distributedLock.js (Atomic Lua Script) 
// Lua script: Atomic multi-key acquisition with instant rollback on collision
const ACQUIRE_SCRIPT = `
local lockValue = ARGV[1]
local ttl = tonumber(ARGV[2])
local acquired = {}

for i, key in ipairs(KEYS) do
  local result = redis.call('SET', key, lockValue, 'NX', 'EX', ttl)
  if not result then
    -- Rollback: release all previously acquired locks in this atomic execution
    for j = 1, #acquired do
      redis.call('DEL', acquired[j])
    end
    return 0
  end
  table.insert(acquired, key)
end
return 1
`;

// Safe release: only delete if lock ownership value matches
const RELEASE_SCRIPT = `
local lockValue = ARGV[1]
local released = 0
for i, key in ipairs(KEYS) do
  if redis.call('GET', key) == lockValue then
    redis.call('DEL', key)
    released = released + 1
  end
end
return released
`;

async function acquireSeatLocks(scheduleId, seatIds, bookingId, ttlSeconds, fromSeq, toSeq) {
  const keys = [...seatIds].sort().map(id => `booking:lock:seat:${scheduleId}:${id}${fromSeq && toSeq ? \`:${fromSeq}:${toSeq}\` : ''}`);
  const lockValue = `${bookingId}:${Date.now()}`;
  const result = await redis.eval(ACQUIRE_SCRIPT, keys.length, ...keys, lockValue, ttlSeconds);
  return { acquired: result === 1, lockValue };
}

async function cleanExpiredBookings() {
  // 1. Elect single leader across all horizontal replicas
  const isLeader = await tryAcquireLeadership();
  if (!isLeader) return;

  const expiredBookings = await prisma.booking.findMany({
    where: { status: { in: ['PENDING', 'SEATS_HELD', 'PAYMENT_PENDING'] }, lockExpiresAt: { lt: new Date() } },
    include: { seats: true }
  });

  for (const booking of expiredBookings) {
    // 2. Optimistic Concurrency Control (CAS): Atomic claim checking version
    const claimed = await prisma.booking.updateMany({
      where: { id: booking.id, version: booking.version, status: { in: ['PENDING', 'SEATS_HELD', 'PAYMENT_PENDING'] } },
      data: { status: 'EXPIRED', failureReason: 'booking_timeout', version: { increment: 1 } }
    });

    // If payment webhook already incremented version, claimed.count is 0 -> skip!
    if (claimed.count === 0) continue;

    // 3. Compensate all completed saga steps & release distributed seat locks
    await compensateAll(booking.id);
    await forceReleaseSeatLocks(booking.scheduleId, booking.seats.map(s => s.seatId));
  }
}

function withDLQ(producer, dlqTopic, logger, handler) {
  const retryMap = new Map();

  return async ({ topic, partition, message }) => {
    const msgKey = `${topic}:${partition}:${message.offset}`;
    const attempt = (retryMap.get(msgKey) || 0) + 1;
    retryMap.set(msgKey, attempt);

    try {
      const parsedValue = JSON.parse(message.value.toString());
      await handler({ topic, partition, message, parsedValue });
      retryMap.delete(msgKey);
    } catch (error) {
      if (attempt >= DLQ_MAX_RETRIES) {
        await producer.send({
          topic: dlqTopic,
          messages: [{
            key: message.key, value: message.value,
            headers: { ...message.headers, 'dlq-original-topic': topic, 'dlq-error': error.message }
          }]
        });
        retryMap.delete(msgKey);
      } else {
        throw error; // Re-throw so KafkaJS retries
      }
    }
  };
}

Senior Engineer & System Design Interview Q&A

16 high-impact questions Principal Engineers and Hiring Managers will ask, and how to deliver compelling answers

Q1 How do you guarantee two concurrent users don't book the exact same train seat at the same millisecond?

"Through Pessimistic Row-Level Locking with NOWAIT inside a PostgreSQL ACID transaction, combined with an exponential backoff retry strategy."

When a user requests a seat hold, the Inventory Service initiates a database transaction executing SELECT id FROM seat_inventories WHERE ... FOR UPDATE NOWAIT.

If another transaction currently holds the row lock, PostgreSQL immediately throws an error (error code 55P03) rather than blocking the thread pool. The request enters an in-memory retryTransaction loop with exponential jitter (100ms, 200ms, 400ms). If the seat cannot be locked within 3 retries, we return an HTTP 409 Conflict with code SEATS_UNAVAILABLE.

INTERVIEWER IMPRESSION: Proves you know the difference between blocking locks (which exhaust connection pools) and non-blocking NOWAIT with retries under high concurrency.
Q2 How do you handle distributed transactions across multiple microservices without Two-Phase Commit (2PC)?

"By implementing an Orchestration-based Saga pattern backed by a persistent SagaLog audit table."

Two-Phase Commit introduces high latency, synchronous blocking, and single points of failure. In TrainTravel, the Booking Service acts as the Saga Orchestrator:

1. Forward Flow: It sequentially calls HOLD_SEATS in Inventory Service $\rightarrow$ CREATE_PAYMENT in Payment Service $\rightarrow$ CONFIRM_SEATS upon successful payment webhook.
2. Compensation Flow: If payment fails or the user cancels, the orchestrator triggers compensating actions in reverse order: compensateCreatePayment (initiates refund with idempotency key) $\rightarrow$ compensateHoldSeats (deletes segment locks and re-opens seats).

INTERVIEWER IMPRESSION: Demonstrates advanced distributed systems design, CAP theorem understanding, and real-world failure recovery mechanisms.
Q3 How does your system allow one seat to be booked by passenger A from Station 1 to 3, and passenger B from Station 3 to 5 on the same train?

"By decoupling physical seats from journey segments using interval overlap algebra in a dedicated seat_segment_locks table."

Every station along a route is assigned a sequential integer (sequenceNumber). When booking a segment from Station $A$ to Station $B$, two intervals $[fromSeq_1, toSeq_1]$ and $[fromSeq_2, toSeq_2]$ overlap if and only if:
fromSeq_1 < toSeq_2 AND toSeq_1 > fromSeq_2.

Since $[1, 3]$ and $[3, 5]$ do not overlap ($1 < 5$, but $3 \ngtr 3$), the query finds zero conflicting rows. Both passengers are successfully allocated the same physical seat number for different segments of the train's route!

INTERVIEWER IMPRESSION: Shows mathematical problem solving applied to revenue optimization in transport and logistics domains.
Q4 Why did you choose Apache Kafka over RabbitMQ or synchronous HTTP for notifications and inventory updates?

"For high-throughput log persistence, consumer decoupling, replayability, and independent consumer scaling."

1. Non-Blocking User Experience: Sending emails via SMTP or third-party gateways (SendGrid) can take 1,500ms. With Kafka, the Booking Service emits booking.confirmed in 2ms and returns HTTP 200 immediately.
2. Fan-out Architecture: When an Admin creates a schedule, both Inventory Service and Search Service consume the event simultaneously at their own processing speeds.
3. Dead Letter Queues (DLQ): If a consumer crashes on a poison message, it routes to a DLQ after 3 retries without blocking partition offsets.

INTERVIEWER IMPRESSION: Demonstrates clear architectural trade-off analysis between message queuing (RabbitMQ) vs distributed event streaming (Kafka).
Q5 How does your background seat lock expiration job run safely when you scale to 5 instances of Inventory Service?

"Through non-blocking PostgreSQL session advisory locks: SELECT pg_try_advisory_lock(800001)."

If 5 microservice instances run a cleanup cron every 15 seconds, having all 5 simultaneously execute DELETE FROM seat_segment_locks WHERE lockExpiresAt < NOW() causes severe database row lock contention and duplicate Kafka event broadcasts.

Using pg_try_advisory_lock(800001), only the first instance that calls the query becomes the leader and obtains a lock. The other 4 instances receive acquired = false and exit immediately without querying seat tables.

INTERVIEWER IMPRESSION: Proves you design for horizontal scalability and distributed concurrency out-of-the-box.
Q6 How does your authentication system prevent refresh token theft and replay attacks?

"Through Refresh Token Rotation with single-use JTI tracking scoped to device IDs in Redis."

When a user logs in, we generate a cryptographically random UUID jti and issue a signed Refresh Token. Redis stores refresh:{userId}:{deviceId} -> jti with a 7-day TTL.

When the token is exchanged, we verify that the incoming JWT's jti matches Redis. If it matches, we immediately generate a brand-new newJti and overwrite Redis. If an attacker intercepts and attempts to reuse the previous refresh token, the jti will mismatch, and we immediately delete all sessions for that device, locking out the attacker!

INTERVIEWER IMPRESSION: Demonstrates production-grade application security, OWASP guidelines, and token lifecycle management.
Q7 Why did you bypass JSON body-parsing specifically for the Razorpay webhook route in the API Gateway?

"Because cryptographic HMAC-SHA256 signature verification requires the exact raw byte stream from the HTTP request."

Standard express.json() parses payloads into JavaScript objects. When re-stringifying them, differences in whitespace, line breaks, or key ordering break the signature check, leading to false "Invalid Webhook Signature" errors.

In api-gateway/src/index.js, I added conditional middleware: if req.path === '/api/payments/webhooks/razorpay', we invoke express.raw({ type: 'application/json' }) to pass the unparsed buffer directly to the Payment Service for secure HMAC validation.

INTERVIEWER IMPRESSION: Shows deep practical experience with payment gateways, webhook security, and Node.js stream internals.
Q8 How do you prevent counter drift between total seats, available seats, and booked seats under extreme concurrency?

"By deriving aggregate counts from actual seat row states using atomic SQL COUNT(*) FILTER (WHERE status = ...) queries inside the transaction."

In high-throughput systems, using naive increment/decrement counters like available = available - 1 leads to counter drift over time due to interrupted rollbacks, network timeouts, or unhandled exceptions.

In recountScheduleAggregates(), we run a single atomic query across seat_inventories:
SELECT COUNT(*) FILTER (WHERE status = 'AVAILABLE') AS available, COUNT(*) FILTER (WHERE status = 'LOCKED') AS locked, COUNT(*) FILTER (WHERE status = 'BOOKED') AS booked.
This guarantees that the schedule table is always an exact mathematical reflection of the underlying seat inventory rows.

INTERVIEWER IMPRESSION: Highlights database integrity discipline and understanding of defensive backend engineering.
Q9 How does your Payment Service guarantee idempotency when Razorpay retries webhook deliveries?

"By recording the payment order event key in an atomic idempotency_records table before executing state mutations."

Payment gateways retry webhook deliveries up to 5 times if their HTTP request times out. In payment-service, we construct a deterministic key PAYMENT_SUCCESS:${gatewayPaymentId}.

Inside a PostgreSQL transaction, we attempt to insert this key with a unique constraint. If a duplicate delivery arrives, PostgreSQL throws a unique violation error, allowing us to immediately return an HTTP 200 OK to Razorpay without re-executing booking confirmations or re-firing Kafka events.

Q13 Why did you execute Lua scripts in Redis instead of standard Redis transactions (MULTI / EXEC) for multi-seat locking?

"Because MULTI / EXEC cannot inspect intermediate state or branch conditionally, whereas Lua scripts execute atomically and can roll back mid-flight."

In Redis, commands inside a MULTI block are queued and executed blindly. If you need to lock 4 seats for a family, you cannot check if Seat 3 is already occupied while processing Seat 2. If one seat is taken, standard commands would still lock the remaining three, leaving the user with an invalid partial reservation.

In booking-service/src/utils/distributedLock.js, our Lua script runs atomically on Redis's single event loop. It loops over all seat keys: if any key already exists, it immediately unrolls all previously acquired keys in that exact execution and returns 0. Furthermore, we pre-sort seat IDs lexicographically ([...seatIds].sort()) to guarantee deterministic lock acquisition order, mathematically preventing circular wait deadlocks across concurrent requests!

INTERVIEWER IMPRESSION: Demonstrates mastery of Redis internals, atomicity primitives, and fundamental distributed deadlock prevention.
Q14 How does your background booking expiry worker prevent race conditions with a concurrent Razorpay payment confirmation webhook?

"Through Optimistic Concurrency Control (CAS) using a monotonic version column on the Booking entity."

Consider a dangerous race condition: A user completes payment at second 599. At second 600, Razorpay's webhook hits payment-service, while simultaneously the background expiry cron job in booking-service wakes up to clean bookings older than 10 minutes.

To prevent cancelling a successfully paid ticket, cleanExpiredBookings() queries the booking with its current version, and performs an atomic Compare-And-Swap update:
prisma.booking.updateMany({ where: { id: booking.id, version: booking.version, status: { in: ['PENDING', 'SEATS_HELD', 'PAYMENT_PENDING'] } }, data: { status: 'EXPIRED', version: { increment: 1 } } }).
If the payment webhook confirms first, it increments version. The expiry job's claimed.count evaluates to 0, causing it to safely back off without cancelling the booking or releasing the customer's seats!

Q15 How do you protect your email OTP authentication flow from side-channel timing attacks and brute-force harvesting?

1. Timing Attack Immunity: Standard JavaScript string comparisons (===) short-circuit at the first non-matching byte. Q16 How does the React frontend prevent token refresh stampedes when multiple parallel API queries fail simultaneously with 401 Unauthorized?
